# SimRealtimeMazurkaBenchmark

A benchmark for **simulated real-time (online) audio-to-audio alignment**, built on the
Chopin Mazurka recordings, with a second benchmark on the Vienna 4x22 piano corpus. Each
scenario pairs two recordings of the same piece; a system must align the query to the
reference while only ever seeing the query up to the current frame. Alignments are scored
against beat annotations.

This repository holds the Mazurka and Vienna 4x22 experiments of *A Simple Alternative to
Online Time Warping*. The alignment algorithms themselves live in the
[OnlineAlignment](https://github.com/HMC-MIR/OnlineAlignment) package (pinned to v0.4.1 in
`environment.yml`); the paper's Piano Concerto experiments and timing study are in
[PianoConcertoAccompaniment](https://github.com/HMC-MIR/PianoConcertoAccompaniment/tree/icassp).
This repository is the benchmark harness around the algorithms: scenario generation,
baselines, evaluation, and the figures.

## Quickstart

Everything runs through `benchmark.py`. The notebooks are thin wrappers around the same
commands, for stepping through the pipeline interactively.

```bash
conda env create -f environment.yml
conda activate sim-realtime-mazurka

# smoke test: 45 scenarios (needs the Mazurka data, see Dataset below)
python benchmark.py run --benchmark train_small --systems DTW SOA --jobs 8
```

The four stages can also be run separately:

```bash
python benchmark.py prepare    --benchmark test                    # build scenario dirs
python benchmark.py features   --benchmark test                    # cache chroma features
python benchmark.py experiment --benchmark test --systems DTW SOA --jobs 8
python benchmark.py evaluate   --benchmark test                    # score against annotations
```

Useful flags: `--config <file.json>` to override system parameters, `--jobs N` to run
scenarios in parallel, and `--resume` to keep results already on disk instead of clearing
each system directory.

## Reproducing the paper

The paper's Table 1 reports the Mazurka test set (3802 pairs) and Vienna 4x22 (924
pairs). With the data in place (see Dataset and Vienna 4x22 below), each benchmark is:

```bash
python benchmark.py prepare  --benchmark test
python benchmark.py features --benchmark test
python benchmark.py experiment --benchmark test --jobs 8 \
    --systems DTW SOA SOA_MONOTONIC OLTW_OURS OLTW_GLOBAL OLTW MM_DIXON MM_ARZT
python benchmark.py evaluate --benchmark test
```

and the same with `--benchmark vienna4x22`. `OLTW` needs the MATCH jar and `MM_DIXON` /
`MM_ARZT` the MatchMaker environment (see Systems). Then

```bash
python -m scripts.compare_benchmarks --benchmarks test vienna4x22 --out results/cross_corpus.csv
```

writes the error rates of the paper's systems on both benchmarks to
`results/cross_corpus.csv` (committed). `docs/running_the_benchmark.md` records how the
runs were made, how long they take, and the failures to expect.

| key | Table 1 column | parameters (`configs/default_systems.json`) |
|---|---|---|
| `DTW` | DTW | offline; steps (1,1), (1,2), (2,1), weights 1, 1, 2 |
| `OLTW` | OLTW | Dixon's Java implementation, its own spectral features |
| `MM_DIXON` | MM-Dixon | MatchMaker, 10 s window |
| `MM_ARZT` | MM-Arzt | MatchMaker, 10 s window, step size 3 |
| `OLTW_OURS` | OLTW-Ours | window of 500 frames (11.6 s) |
| `OLTW_GLOBAL` | OLTW-Global | unbounded window |
| `SOA` | SOA | steps (1,1), (1,2), (2,1), weights 1, 1, 2 |
| `SOA_MONOTONIC` | SOA-Mono | as SOA, estimates forced monotonic |

All systems but `OLTW` use chroma STFT features and cosine distance. DTW is scored on
3795 of the 3802 test pairs: on
7 pairs the recordings differ in length by more than its slope limit allows (details in
`docs/running_the_benchmark.md`).

## Dataset

`benchmark.py` expects each corpus at the repository root, in the same shape:

```
Chopin_Mazurkas/
├── wav_22050_mono/<piece>/<recording>.wav      # 22.05 kHz mono
└── annotations_beat/<piece>/<recording>.beat   # beat annotations
```

The recordings and annotations come from the [Mazurka Project](http://mazurka.org.uk/) and
are not redistributed here. Two recordings are left out of every benchmark because their
beat annotations cannot be matched beat for beat with the other recordings of their
piece (they follow a different form); see `EXCLUDED_RECORDINGS` in `corpora/mazurkas.py`. The data is not committed, and neither are the scenario,
feature, experiment, or evaluation directories — all of them are regenerated by
`benchmark.py`. Note in particular that scenario directories contain **absolute** symlinks
into `Chopin_Mazurkas/`, so they must be regenerated after cloning or moving the repository.

### Vienna 4x22

The optional `vienna4x22` benchmark uses the [Vienna 4x22 Piano
Corpus](https://github.com/CPJKU/vienna4x22): 22 pianists playing each of four
excerpts, recorded on a Bösendorfer SE290 as audio and MIDI at once. It ships neither
audio nor beat annotations, so both are produced locally:

```bash
git clone https://github.com/CPJKU/vienna4x22
curl -L -O https://repo.mdw.ac.at/projects/IWK/the_vienna_4x22_piano_corpus/data/audio.zip  # 1.3 GB
unzip audio.zip -d vienna4x22_audio

python -m scripts.vienna4x22.verify_timebase --audio-dir vienna4x22_audio --match-dir vienna4x22/match
python -m scripts.vienna4x22.prepare        --audio-dir vienna4x22_audio --match-dir vienna4x22/match
python benchmark.py run --benchmark vienna4x22 --systems DTW SOA --jobs 8
```

Annotations are derived from the corpus's score-to-performance match files: each score
beat is timed by the median onset of the notes aligned to it. Positions are chosen once
per piece and shared by all 22 performances, because `eval_tools` pairs the query's and
reference's annotations row by row. Rolled chords are excluded, since no single
timestamp represents them — the final chord of the op. 38 Ballade spans over 5 s in
some performances.

**Run `verify_timebase` first.** The annotations are correct only if match-file times
are audio times. The script detects onsets in each recording and checks them against the
match file's note onsets over a range of shifts; with the current corpus all 88
recordings match best at a shift of zero, so no correction is needed. If a future
revision of the corpus reports offsets, feed them back with `prepare --offsets`.

Note that all 22 performances of a piece share one instrument, room and microphone
setup. That removes the recording-condition variation that dominates the Mazurka set,
so this benchmark isolates tempo and expressive variation and its error rates are not
interchangeable with the Mazurka ones. Its ground truth also comes from a reproducing
piano's MIDI capture rather than human beat tapping, a different noise floor.

## Benchmarks

| benchmark | pieces | scenarios | purpose |
|---|---|---|---|
| `train_small` | 10 recordings of Op. 17 No. 4 | 45 | quick smoke test |
| `train` | all recordings of Op. 17 No. 4 | 1953 | parameter tuning |
| `test` | Op. 24 No. 2, Op. 30 No. 2, Op. 68 No. 3 | 3802 | reported results |
| `vienna4x22` | 4 excerpts × 22 pianists (Vienna 4x22) | 924 | cross-corpus check |

Each benchmark writes to its own set of directories (`scenarios*/`, `experiments*/`,
`eval*/`); see `BENCHMARK_CONFIGS` in `corpora/benchmarks.py`.

### Adding a benchmark

`corpora/` holds everything that knows where data lives. A corpus records the audio
and annotation roots for one collection of recordings; a benchmark names a corpus plus
the pieces to draw from, and the directories to write to. Nothing downstream of
scenario generation is corpus-aware: the systems, `eval_tools.py`, and the notebooks
see only the per-scenario symlinks.

So a new benchmark over an existing corpus is one entry in `BENCHMARK_CONFIGS`, and a
new corpus is one `Corpus` in `corpora/` plus its registry entry. Benchmarks that
declare `piece_roots` enumerate their recordings from disk and write the result back to
`cfg/`; the older `train` benchmarks instead read a checked-in list, and set
`default_piece_root` because those lists store bare recording names.

## Systems

`--systems` takes the keys below.

| key | description | extra requirements |
|---|---|---|
| `DTW` | offline DTW reference (not real-time) | — |
| `SOA` | Simple Online Alignment | — |
| `SOA_MONOTONIC` | as above, predictions forced monotonic | — |
| `OLTW_GLOBAL` | our OLTW, unconstrained | — |
| `OLTW_OURS` | our OLTW, constrained window | — |
| `OLTW` | Dixon's OLTW via `PerformanceMatcher.jar` | Java 21+, `match/PerformanceMatcher.jar` |
| `MM_DIXON` | [MatchMaker](https://github.com/pymatchmaker/matchmaker) OLTW, Dixon variant | `matchmaker` env |
| `MM_ARZT` | MatchMaker OLTW, Arzt variant | `matchmaker` env |
| `MATCH` | Dixon's MATCH via the Vamp plugin (not in the paper) | `sonic-annotator`, match-vamp-plugin |

The paper writes the keys as in the table under Reproducing the paper (e.g. `OLTW_OURS`
as OLTW-Ours, `MM_ARZT` as MM-Arzt); `SYSTEM_DISPLAY_NAMES` in `utils/constants.py`
handles that at plot time, so directory names stay stable.

### Dixon's OLTW (MATCH)

`OLTW` runs Simon Dixon's original Java implementation of on-line time warping, from the
MATCH toolkit (Dixon and Widmer, "MATCH: A Music Alignment Tool Chest", ISMIR 2005; main
class `at.ofai.music.match.PerformanceMatcher`). Download `PerformanceMatcher.jar` and
place it at `match/PerformanceMatcher.jar` (the `match/` directory is not committed). The
jar needs Java 21 or later, which `environment.yml` installs; `utils/oltw.py` prefers the
environment's Java over one on the system `PATH`.

Default parameters are in `configs/default_systems.json`; see `configs/README.md` for the
parameter reference and the tuning sweeps.

### MatchMaker baselines

`pymatchmaker` pins `numpy<2`, so the MatchMaker systems run out-of-process in their own
environment, which pins `pymatchmaker==0.3.0` (the version `utils/matchmaker_worker.py`
requires):

```bash
conda env create -f environment-matchmaker.yml
export MATCHMAKER_PYTHON=$(conda run -n matchmaker which python)   # optional
python benchmark.py experiment --benchmark test --systems MM_DIXON MM_ARZT
```

If `MATCHMAKER_PYTHON` is unset, `utils/matchmaker_baseline.py` looks for an env named
`matchmaker` alongside the active one.

## Notebooks

| notebook | purpose |
|---|---|
| `01_DataPrep.ipynb` | scenario generation and feature caching (`prepare`, `features`) |
| `02_RunExperiment.ipynb` | running systems and parameter sweeps (`experiment`) |
| `03_Evaluate.ipynb` | error rate table and error-vs-tolerance figures (`evaluate`) |
| `04_Analysis.ipynb` | per-scenario alignment path and error plots |

Notebooks 01-03 shell out to `benchmark.py` rather than reimplementing it, so the notebook
and command-line paths cannot drift. Figures are written to `figures/` and the aggregate
error rate table to `results/`. Saving the plotly figures as images uses `kaleido`, which
needs a Chrome or Chromium installation.

## Layout

```
benchmark.py            pipeline entry point (prepare / features / experiment / evaluate / run)
eval_tools.py           alignment scoring against beat annotations
utils/
  experiments.py        ExperimentRunner: dispatches a system over the scenarios
  oltw.py               wrapper around PerformanceMatcher.jar
  matchmaker_baseline.py, matchmaker_worker.py
                        out-of-process MatchMaker baselines
  constants.py          shared defaults and the system display-name map
corpora/                corpora, benchmarks, and excluded recordings
cfg/                    pickled piece and pair lists per benchmark
configs/                system parameter JSON files
results/                aggregate error rate tables (committed)
figures/                generated figures (committed)
```
